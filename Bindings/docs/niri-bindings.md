## How Niri Evaluates Stacked Configurations

---

### 1. The Global Nature of `mod-key`

Niri does not execute your configuration file procedurally line-by-line like a script. Instead, it reads all the files, resolves the `include` statements, and merges everything into a single declarative tree structure *before* the compositor fully applies the settings.

Because `input` is a merged section, **the last defined value for a property wins globally**.

> **What this means for your config:** There is no historical memory where lines 1–809 are evaluated as `Alt` and later lines are evaluated as `Super`. If `basicsettings.kdl` overrides the `mod-key` to `"Super"`, that becomes the global value for the entire compositor session. Consequently, every single instance of the abstract `Mod` keyword across *all* files (including lines 1–809 of `config.kdl`) will expand to `Super`.

### 2. The "Last One Wins" Rule for Binds

For the `binds` section, Niri explicitly allows you to redefine hotkeys. If two different files define a binding for the exact same key combination, the one that is parsed **last** will completely overwrite the previous one.

Since your `include "atmosphera.kdl"` is at the very bottom, any conflicting key combinations defined inside it will successfully override what came before it.

Here is exactly why this is happening and how to fix it.

## Why Your Override is Being Ignored

---

Niri deduplicates and overrides keybindings based on the **exact text string** of the shortcut definition *before* it evaluates what the `Mod` keyword actually means.

Because your upstream files and your custom files use different strings, Niri doesn't realize they are meant to be the same hotkey during parsing:

* **In `keybinds.kdl`:** Niri reads `Mod+W { close-window; }`
* **In `atmosphera.kdl`:** Niri reads `Super+W { spawn "..."; }`

Since `Mod+W` and `Super+W` are literally different strings, Niri keeps **both** bindings in its internal array instead of letting the second one overwrite the first.

### The Runtime Race

At runtime, Niri expands `Mod` to `Super` because of your global setting. Now, its internal active hotkey list looks like this:

1. `Super+W` $\rightarrow$ `close-window;` *(Originally written as Mod+W)*
2. `Super+W` $\rightarrow$ `spawn "...";` *(Originally written as Super+W)*

When you actually press **Super + W**, Niri scans this list from top to bottom. It hits the first match (`close-window`), executes it immediately, and stops searching. Your script never even gets a chance to breathe.

---

## The Fixes

You have two ways to solve this, depending on how you want to manage your files.

### Option 1: Match the Upstream Syntax (Recommended)

The easiest fix is to change the literal `Super` to `Mod` inside your `atmosphera.kdl` file. Since `Mod` expands to `Super` anyway, matching the string exactly forces Niri to overwrite the upstream binding during parsing.

In `atmosphera.kdl`, change it to:

```kdl
binds {
    Mod+W { spawn "/home/user/Projects/atmosphera-bindings/niri/atmosphera-close-tab-or-window"; }
}

```

### Option 2: Kill the Upstream Binding

If you absolutely want `atmosphera.kdl` to use explicit `Super+W` syntax, you must prevent the upstream file from claiming `Mod+W`. Go into your `keybinds.kdl` (or lines 1–809 of `config.kdl`) and comment out or remove the original window-closing bind completely:

```kdl
// Comment this out in your main/upstream files:
// Mod+W { close-window; } 

```

Once `Mod+W` is no longer occupying the top slot in Niri's internal list, your explicit `Super+W` bind at the bottom will capture the keypress perfectly.

## Shifting the Global `mod-key`

---

Inside your `atmosphera.kdl` file (or right at the bottom of your main `config.kdl`), add an `input` block that assigns `mod-key` to a completely different modifier, like `Alt`:

```kdl
input {
    mod-key "Alt"
}

binds {
    Super+W { spawn "/home/user/Projects/atmosphera-bindings/niri/atmosphera-close-tab-or-window"; }
}

```

## How It Solves the Conflict

---

Because Niri applies this setting globally after parsing everything, it retroactively changes the meaning of `Mod` across all the files it just read:

* The upstream binding `Mod+W` gets evaluated as **Alt + W**.
* Your explicit binding remains **Super + W**.

Since `Alt+W` and `Super+W` are entirely different physical key combinations, they will no longer collide, and your script will trigger flawlessly when you press your Windows/Super key.

> **The Side Effect:** Keep in mind that this shifts *every single* upstream binding that relies on the `Mod` keyword over to the `Alt` key. If you are using `atmosphera.kdl` to build out a completely custom, self-contained layout from scratch using explicit `Super+...` strings, this is the perfect way to safely neutralize the default configuration without ever touching the upstream files.

## The Ghost Key Strategy: `ISO_Level5_Shift`

---

Niri's configuration parser strictly validates modifiers, so you cannot pass a completely random string or a `null` value to `mod-key` without throwing a config error. However, Niri explicitly supports a rare modifier called **`ISO_Level5_Shift`**.

Unless you have gone out of your way to configure advanced custom XKB layout options (like mapping your Caps Lock to a Level 5 Switch), **there is no physical key on your keyboard that triggers this modifier.**

By declaring this at the very bottom of your configuration (or inside `atmosphera.kdl`), you can cleanly neutralize the rest of the layout:

```kdl
input {
    mod-key "ISO_Level5_Shift"
}

binds {
    // Your explicit binds remain perfectly active
    Super+W { spawn "/home/user/Projects/atmosphera-bindings/niri/atmosphera-close-tab-or-window"; }
}

```

## Why This Work Flawlessly

---

* **Zero UX Collisions:** Because Niri retroactively changes `Mod` across all parsed files, every single default upstream binding (like `Mod+Q`, `Mod+T`, `Mod+W`) is instantly remapped to require a physical `ISO_Level5_Shift` key.
* **Complete Deactivation:** Since that key cannot be physically pressed, those upstream shortcuts become entirely inert "ghost" binds. They still exist in Niri's registry so the parser stays happy, but they can never be triggered.
* **Immunity for Your Layout:** Because your custom hotkeys in `atmosphera.kdl` explicitly use the literal `Super` string, they are completely unaffected by this modifier swap and will trigger exactly when you want them to.
